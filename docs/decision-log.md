# Rick-Commerce: decision log

The project was named Amspec E-commerce until 2026-10-09 (D-055). Rows written before that date keep the old name.

One record of every significant decision, merged from the six reference documents during Phase 0. Decisions made during the build start at D-050 and are added at the bottom.

The decision tables were removed from the six reference documents on 2026-10-09 (D-053). This file is now the only place decisions are recorded. The headings below show which document each decision first came from.

Each decision has six fields: ID, decision, context, options considered, reason, consequences.

A decision is never deleted or rewritten. If one is reversed, add a new decision that says which one it replaces.

Where a source document gave no context for a decision, the context below was written during the merge from that document's own text. Those rows are D-008 to D-021 and D-024 to D-028.

## D-001 to D-007 · Product Requirements Document

| ID | Decision | Context | Options considered | Reason | Consequences |
| --- | --- | --- | --- | --- | --- |
| D-001 | Use real brand names as text, with a disclaimer | Public portfolio inspired by a real company | Real names plus disclaimer; fictional brands; real names plus real assets | Keeps the tie to the real business with low legal exposure | No logos or real photos; placeholder images; disclaimer on every page (FR-62) |
| D-002 | B2C only; bulk orders go through a quote inquiry form (revised 2026-10-08) | AMSPEC is a manufacturer-distributor, so wholesale is realistic | Retail only; retail plus quote inquiries; retail plus business accounts with tier pricing; full B2B | Tier pricing was first chosen, then dropped as the largest schedule risk. An inquiry form fits a distributor at a fraction of the cost | One inquiry table and an admin inbox; no pricing module; quotes are settled outside the app |
| D-003 | Guest cart, login required at checkout | Balance realism against complexity | Account required for cart; guest cart with login at checkout; full guest checkout | Teaches cart merging without guest-order handling | Needs a guest cart identity and a merge rule (FR-12) |
| D-004 | All catalog data is invented | amspec.ph is offline; real prices are unknown | Scrape retailer listings; invent seed data | Avoids copying and false claims | Seed script is the single source of catalog data |
| D-005 | Gateway-shaped payments: mock provider first, real test-mode adapter later (revised 2026-10-08) | Prototype scope; no real money | Simple mock methods; three direct integrations (GCash, Maya, Dragonpay); one aggregator from day one; gateway-shaped mock, then one aggregator adapter | Teaches webhooks, asynchronous payment and refunds without depending on an outside account from the start | New order state (awaiting payment), webhook endpoint, refund records; PayMongo test mode is the planned adapter |
| D-006 | Decrement stock at order placement, no reservation | Simplest correct inventory model | Reserve on add-to-cart; reserve at checkout start; decrement at order | Fewest moving parts; still teaches transactions and locking | Items can sell out while in a cart |
| D-007 | Track order status and payment status separately | Cash on delivery is unpaid until delivered, so one status list could not describe it | One combined status; separate order and payment statuses | Fulfilment and payment move independently in real stores | Two status fields and two sets of transition rules (FR-35) |

## D-008 to D-015 · Technical Requirements Document

| ID | Decision | Context | Options considered | Reason | Consequences |
| --- | --- | --- | --- | --- | --- |
| D-008 | TypeScript, strict, on client and server | Data passes through several layers between the browser and the database | JavaScript; TypeScript | Type safety across layers; stronger portfolio; matches the developer's target stack | Slightly slower start; build step on the server |
| D-009 | Hand-written SQL with pg | The API needs a way to talk to PostgreSQL | ORM (Prisma, Drizzle); query builder (Kysely); raw SQL | Learning SQL is a stated goal | More boilerplate; row types written by hand |
| D-010 | Server-side sessions in PostgreSQL, httpOnly cookie | The API must know who is calling on every request | JWT in localStorage; JWT in a cookie; sessions | Revocable, simple, safe by default | Session table; cookie and CSRF handling to learn |
| D-011 | Routes, controllers, services, repositories, grouped by feature module | Backend code needs one consistent internal structure | Everything in route handlers; layers grouped by type; feature modules | Clear responsibilities; easy to test services | Four files per feature, even small ones |
| D-012 | Guest cart stored server-side, keyed by session | Guests build a cart before they have an account (D-003) | Cart in localStorage; server-side cart | One cart model for guests and customers; server computes prices | Sessions are created for guests on first add-to-cart |
| D-013 | Integration tests against a real PostgreSQL database | API tests need something to run against | Mocked repositories; real database | Catches SQL, constraint and transaction bugs | Tests need a running database and are slower |
| D-014 | Vite dev proxy instead of CORS in development | The browser app and the API run on different ports in development | Enable CORS; same-origin via proxy | Same-origin cookies behave as in production | CORS is configured for production only |
| D-015 | Status values as text with CHECK constraints | Orders, payments and inquiries each have a fixed list of statuses | PostgreSQL enum types; lookup tables; text with CHECK | Easy to change in a migration | Allowed values are listed in both SQL and TypeScript |

## D-016 to D-021 · Web Application Flow Document

| ID | Decision | Context | Options considered | Reason | Consequences |
| --- | --- | --- | --- | --- | --- |
| D-016 | Single-page checkout with three sections | Checkout collects an address, a payment method and a review | Multi-step wizard; single page | Less state to manage; nothing lost between steps | Longer page on mobile |
| D-017 | Reference numbers in URLs for orders and inquiries | Customers share and bookmark order and inquiry links | Database IDs; UUIDs; reference numbers | Readable, and does not expose row counts through sequential IDs | A unique reference column and a generator |
| D-018 | List state lives in the URL | The product list has search, filters, sort and pages (FR-07) | Component state; global store; URL | Shareable links; back button works | Parsing and validating query parameters on both sides |

| D-020 | Products are created inactive | A product is built up in several steps in the admin editor | Active on create; inactive on create | Prevents half-finished products appearing in the store | Publishing is an explicit step |
| D-021 | Customers and permitted staff can cancel before shipping (revised 2026-10-08) | An order may no longer be wanted after it is placed | Customer and admin; admin only | Requested by the developer; pairs naturally with refunds | Cancel button on order detail; refund path depends on payment method |

## D-024 to D-028 · Technical Requirements Document

| ID | Decision | Context | Options considered | Reason | Consequences |
| --- | --- | --- | --- | --- | --- |
| D-024 | One PaymentProvider interface; a mock provider first | Several payment methods now, and a real provider planned later (D-005) | Call a gateway SDK directly from the order service; provider interface with adapters | The order code never knows which provider is in use, so a real one is added without touching it | A mock gateway to build and maintain; one adapter per provider |
| D-025 | A verified webhook is the only thing that marks a payment paid | Something must decide when an order counts as paid | Trust the browser redirect; poll the provider; webhook | The redirect can be faked or never happen; the webhook comes from the provider's server | Payment is asynchronous; the customer waits on a status page |
| D-026 | Stock is held when the order is created, and released after 30 minutes without payment | Online payment completes some time after the order is created | Decrement only when paid; hold at order creation with expiry | A customer who pays must never find the item sold to someone else meanwhile | An expiry sweep; abandoned payments hold stock for up to 30 minutes |
| D-027 | Role-to-permission map kept in code; one role column on users | The four fixed staff roles (D-022) must be enforced on every admin route | Role checks scattered in routes; roles and permissions tables; permission map in code | Roles are fixed, so tables would add joins and screens with no benefit | Changing a role's permissions needs a code change; custom roles would need the tables |
| D-028 | Expiry sweep runs as an in-process timer | Unpaid orders must be cancelled after their deadline (D-026) | Job queue; cron; in-process timer | Keeps the no-queue constraint; enough for one process | With several API processes the sweep must be made safe to run concurrently |

## D-029 to D-036 · Design Brief

| ID | Decision | Context | Options considered | Reason | Consequences |
| --- | --- | --- | --- | --- | --- |
| D-029 | Original visual identity; mood taken from the business, nothing from the real site | The real site is offline and its assets are not ours to use | Imitate the real brand; original identity | Legally safe and honest about what is known | A wordmark, palette and placeholder images to create |
| D-030 | Paper, ink, one action blue and pencil yellow | School supplies invite a rainbow, which hurts clarity | Multi-colour brand palette; restrained palette with category accents | Colour keeps its meaning for actions and status | Yellow can never carry text; five category accents are decorative only |
| D-031 | Nunito for headings, Inter for body, both self-hosted | Needs to feel friendly but stay readable in tables and prices | System fonts; one typeface; two typefaces | Personality in headings, precision in data | Two font packages; slightly larger first load |
| D-032 | Generated placeholder tiles as product images | No rights to real product photos | Retailer photos; stock photos; generated tiles | Consistent, honest and free of copyright risk | Catalog looks plainer than a real store |
| D-033 | No add-to-cart button on product cards | Most products have variants | Quick-add on cards; add only from the product page | Avoids adding the wrong pack size; one less flow to build | One extra tap for single-variant products |
| D-034 | No dark mode in the prototype | Doubles the visual checking for every screen | Light only; light and dark | Keeps effort on the commerce and payment logic | Tokens are named so a dark theme can be added later |
| D-035 | Tailwind's default spacing scale and breakpoints | A custom system adds decisions without adding value | Custom scale; Tailwind defaults | Well documented and one less thing to maintain | Design values must snap to the default steps |

## D-037 to D-044 · Backend Schema Document

| ID | Decision | Context | Options considered | Reason | Consequences |
| --- | --- | --- | --- | --- | --- |
| D-037 | One users table for customers and staff, with a role column | Both log in the same way with an email | Separate customer and staff tables; one table | One login flow, one session model | Every staff-only rule must check the role; registration must never accept a role |
| D-038 | Brand is a text column on products | Brand pages are not in the prototype | brands table; text column | One less table and join for a filter | Brand spelling must be consistent in seed and admin input; a migration is needed if brand pages are built |
| D-039 | Keep a stock number on the variant and an append-only movement ledger | Stock must be fast to check and fully explainable | Number only; ledger only, summed on demand; both | The number can be locked and checked in one statement; the ledger gives the audit trail | Both must change in the same transaction; a test checks they agree |
| D-040 | Copy the delivery address into columns on the order | Customers edit and delete addresses | Foreign key to addresses; a jsonb snapshot; plain columns | Orders stay correct forever and the columns can be queried and constrained | Eight extra columns on orders |
| D-041 | A payment row per attempt, with partial unique indexes for "one paid" and "one pending" | Customers retry after failures; webhooks can race | Payment fields on the order; one payment row per order; a row per attempt | Keeps failure history and lets the database refuse a double payment | Retry is only possible once the open attempt has ended |
| D-042 | No deleted_at columns; an is_active flag where rows must be kept | Orders and logs reference catalog rows and users | Soft delete with timestamps; active flag; hard delete | Simplest thing that keeps history intact | Every storefront query must filter on is_active |
| D-043 | updated_at is maintained by a database trigger | Easy to forget in application code | Set it in every repository function; trigger | Cannot be forgotten, and it teaches triggers | One trigger function and a trigger per mutable table |
| D-044 | The expiry timer uses FOR UPDATE SKIP LOCKED | Decision D-028 noted the timer is unsafe with several server processes | Advisory lock; leader election; skip locked rows | One clause, built into PostgreSQL | None for the prototype; it is simply safe if scaled |

## D-045 to D-049 · Development and Implementation Plan

| ID | Decision | Context | Options considered | Reason | Consequences |
| --- | --- | --- | --- | --- | --- |
| D-045 | Finish the retail loop with cash on delivery before building online payment | Payments are the largest and riskiest part | Build payments together with checkout; cash on delivery first | Order and stock logic are learned and tested alone; a clean cut line exists | Checkout is touched twice |
| D-046 | Build admin screens after the storefront and payments | Admin work needs orders and payments to exist | Admin first; storefront first | Seed data covers the catalog until then; staff features can be tested against real orders | No admin screens until Milestone 5 |
| D-047 | Two working modes chosen by phrase, with hats off as default | The developer wants depth but found typing everything too slow | Developer types all; mentor writes all; switchable | Depth where it matters, speed elsewhere | The explain-back gate is required in both modes |
| D-048 | Bulk inquiries are the developer's solo phase | A complete small feature with no risky logic | Mentor-led like the others; solo | Tests whether the patterns have been learned | Slower, with review instead of guidance |
| D-049 | No calendar dates in the plan | Part-time work with learning gates | Dated schedule; relative sizes | A date would be a guess and would pressure the gates | Progress is tracked by milestone, not by week |
